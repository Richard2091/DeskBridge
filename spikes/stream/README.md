一次性的验证代码，**不是正式代码**。目的是补齐 [results.md](../results.md)“未验证事项和测试缺口”中的 1–4 条：经过 Tailscale 的传输、30/60 fps、视频编码和真实使用目标，再据此决定客户端框架（[ADR-0002](../../docs/decisions/adr-0002-ui-framework.md)）。

设计上参考 RustDesk（采集、硬件优先的编码、码率和帧率自适应），只参考设计，不复制代码。

本文只定义“测什么、怎么测、怎么记录”。代码和结果分别在后续子任务中完成，结果写入 `results.md`。

## 档位

| 档位 | 用途 | 分辨率 | 帧率 | 编码 | 起始码率 |
|---|---|---|---|---|---|
| 观屏 | AI 看屏幕，人偶尔看一眼 | 原始分辨率 | 1–5 fps，画面不变时不发 | H.264；另测每帧 JPEG 作对照 | 不限，记录实际值 |
| 普通控制 | 人操作远程桌面 | 1920×1080 | 30 fps | H.264 | 4 Mbps |
| 高帧率 | 看视频、拖动窗口等 | 1920×1080 | 60 fps | H.264 | 8 Mbps |
| 4K | 4K 屏幕原样传输 | 3840×2160 | 30 fps，能跑再试 60 fps | H.264 | 12 Mbps |

- 起始码率只是起点，测试中可以调整，结果里记录实际使用的值。
- 屏幕分辨率不等于档位分辨率时，在被控端缩放后再编码，并记录缩放的耗时。
- 编码统一用低延迟设置：不用 B 帧，编码器不缓存帧；关键帧在开始和丢包恢复时按需生成，其余时间不定期插入。
- 只测 H.264。它是 WebView2（WebCodecs）、安卓 MediaCodec 和各家硬件编码器都支持的格式。H.265、VP9、AV1 先记为“待验证”，H.264 达不到要求时再测。
- 每个档位分别测硬件编码和软件编码。

## 测试画面

被控端运行一个测试画面程序，全屏显示，内容分三种：

| 场景 | 内容 | 看什么 |
|---|---|---|
| 静止 | 桌面不动，只有测试时钟在变 | 空闲时的码率和资源占用 |
| 文字 | 一段文字自动滚动 | 日常操作的情况；文字是否清楚 |
| 高运动 | 全屏移动的色块和渐变 | 最坏情况下的码率、丢帧和编码耗时 |

每种场景的画面上都有两样东西：

1. **人能读的毫秒时钟**：大号数字，用于截图和拍照校验。
2. **机器能读的时间戳**：把 32 位的帧编号或毫秒时间编成一排黑白方块，每块不小于 16×16 像素，压缩后仍能准确读回。控制端解码后读取这块区域，得到画面绘制的时间。

## 延迟

延迟不设硬性要求（Tailscale 中继本身就可能超过 150 ms），但要拆开记录，弄清时间花在哪里。

### 网络延迟

- `tailscale ping`：记录连接方式（直连或经过哪个中继）和往返时间。
- 程序内的往返测量：在画面流的同一条连接上每秒发一次小包并回显。分别在**空闲**和**推流时**测量，推流时的增量说明排队有多严重。

### 管线延迟

每一帧在各阶段打上时间戳：

| 代号 | 时刻 | 在哪台机器 |
|---|---|---|
| T0 | 测试画面程序绘制这一帧 | 被控端 |
| T1 | 采集得到这一帧 | 被控端 |
| T2 | 编码完成 | 被控端 |
| T3 | 写入连接 | 被控端 |
| T4 | 收到完整的一帧 | 控制端 |
| T5 | 解码完成 | 控制端 |
| T6 | 提交显示 | 控制端 |

- T1–T3 跟着帧一起发出；T4–T6 由控制端记录。
- T6 是程序提交绘制的时刻，不含显示器扫描输出。界面框架没有提供更准确的时刻时，取提交后的下一帧回调时间，并在结果中说明。
- 每个指标记录 p50、p95、最大值。还要看延迟是否随测试时间增长；持续增长说明帧在某处堆积。

### 两端时钟的问题

| 测试方式 | 怎么算 |
|---|---|
| 同一台机器（本机回环、经中继绕回本机） | 两端用同一个时钟，各时刻直接相减 |
| 两台机器 | 时钟不同步，不直接相减。控制端显示一帧后把帧编号回传给被控端，被控端算出往返时间 T0 → 回传到达。单程管线延迟约等于往返时间减去程序测得的网络单程（推流时往返时间的一半）。各阶段的耗时（编码 T2−T1、解码 T5−T4）只用本机时钟，不受影响 |

“经中继绕回本机”是指被控端把画面发给 Linux 转发端，再转发回同一台 Windows 上的控制端。两段都走中继，测到的网络延迟是一次远程连接的两倍，但时钟是同一个，结果最准确。

### 校验

- 同一台机器：截一张整屏截图，同时包含原始测试时钟和控制端窗口里的时钟，两者之差就是这一刻的显示延迟。每档位截 10 张。
- 两台机器：用另一部手机或相机同时拍下两块屏幕，读两个时钟之差。只做少量抽查，用来核对上面算法的结果。

## 资源和画面指标

每秒采样一次，每次测试先预热 5 秒，再记录 20 秒。最初定为预热 10 秒、记录 60 秒；台式机上两种时长的结果相差不到 0.4 ms 和 0.3 个百分点（见 `spikes/results.md`），为节省测试时间缩短。码流和时间戳只抽查 3 项。

| 指标 | 被控端 | 控制端 | 采集方式 |
|---|---|---|---|
| CPU | 采集和编码进程 | 界面进程及子进程（含 WebView2） | 进程 CPU 时间，按逻辑核心总数换算成整机百分比，同时记录核心数 |
| GPU | 视频编码引擎、3D 引擎 | 视频解码引擎、3D 引擎 | Windows 性能计数器 `GPU Engine` 按引擎类型统计；NVIDIA 另用 `nvidia-smi` 核对 |
| 内存 | 私有内存峰值 | 私有内存峰值（含 WebView2 进程树） | 进程计数器 |
| 码率 | 平均和峰值（每秒字节数），关键帧大小 | 实际收到的码率 | 程序统计 |
| 帧率和丢帧 | 采集帧数、编码帧数、编码器跳过的帧数 | 收到、解码、显示的帧数；“只保留最新帧”丢掉的帧数 | 程序统计 |
| 手机（控制端为手机时） | — | 电池温度、10 分钟耗电、显示帧率 | `adb shell dumpsys battery`；程序统计 |

## 网络场景

| 场景 | 路径 | 说明 |
|---|---|---|
| 本机回环 | A → A，`127.0.0.1` | 基准，只有管线延迟 |
| 局域网直连 | A ↔ P | 同一路由器下，Tailscale 直连 |
| 中继，绕回本机 | A → L → A | 两段都经过中继，同一时钟 |
| 中继，两台电脑 | A ↔ B | 两台电脑之间经中继 |
| 人为劣化 | A → L → A，L 上加 `tc netem` | 增加延迟、抖动和丢包，具体参数在网络传输子任务中确定 |

两台电脑不在同一局域网，局域网场景只能用本机回环和手机代替。

公共中继可能限速（待验证），需要记录能达到的最大吞吐。中继走 TCP，丢包时后面的数据要等重传（队头阻塞），在人为劣化场景中观察影响。

## 记录格式

每次测试输出一个 JSON 文件，至少包含：

- 测试条件：档位、场景、网络场景、编码器（硬件或软件、具体名称）、码率、两端设备代号、界面框架和送帧方式。
- 网络：连接方式、空闲和推流时的往返时间。
- 各阶段延迟的 p50、p95、最大值。
- 各资源指标的平均值和峰值。
- 帧数统计和丢帧率。

原始文件放在 `spikes/stream/out/`，不提交（可能含真实地址和设备名），只把汇总表写进 `results.md`。

## 判断方法

不设通过线，主要用来比较。重点看：

1. 每个档位能否稳定达到目标帧率（显示帧率不低于目标的 90%）。
2. 延迟是否稳定，不随时间增长；网络之外的管线延迟各框架相差多少。
3. 相同条件下，各框架和 RustDesk 的资源占用差多少（任务 24.5）。
4. 手机能否流畅显示 1080p 30 fps（任务 24.6）。

## 程序（任务 24.2）

`rs/` 是 Rust 写的两个程序，只在 Windows 上编译（`rs\build.cmd`）。

| 程序 | 作用 |
|---|---|
| `pattern.exe` | 在主屏全屏显示测试画面，`--scene static\|text\|motion`。按 Esc 或到时间后退出 |
| `capenc.exe list` | 列出显卡、显示输出和系统里的 H.264 编码器 |
| `capenc.exe run` | 采集、转换、编码并测量。`--pattern` 同时启动测试画面；`--width`、`--fps`、`--kbps`、`--encoder hw\|sw`、`--seconds`、`--warmup`；`--out`、`--stats` 保存码流和逐帧记录 |
| `capenc.exe verify` | 用微软软件解码器解码保存的码流，逐帧比对画面里的时间戳，`--png` 导出一帧 |

处理流程：

1. DXGI Desktop Duplication 取得新画面，复制到自己的 BGRA 纹理。
2. 按目标帧率排发送时刻；来不及发送就被新画面覆盖的帧只计数，不编码。
3. D3D11 视频处理器在显卡上缩放并转成 NV12（BT.709，16–235）。
4. Media Foundation 编码：硬件编码器直接读显卡纹理；软件编码器（微软自带）先读回内存。低延迟模式，固定码率，只在开头生成关键帧。
5. 每秒采样本进程 CPU、私有内存和显卡各引擎占用（性能计数器 `GPU Engine`，用英文名添加，中文系统也能用）。

`matrix.py` 在 Linux 上通过 agentdesk 批量运行各档位。执行器单次调用约 36 秒超时，所以程序在后台启动，结果写到文件后再读取。

测得的延迟是这几段：

| 名称 | 含义 |
|---|---|
| `draw_to_capture` | T0 → T1：测试画面绘制到采集得到，包含系统合成画面的等待 |
| `present_to_capture` | 系统显示这一帧到采集得到 |
| `capture_to_encoder_input` | T1 → 送入编码器：主要是等待下一个发送时刻 |
| `encoder_input_to_output` | 送入编码器到交出码流，包含显卡上的缩放和颜色转换 |
| `draw_to_encoded` | T0 → T2 合计 |
